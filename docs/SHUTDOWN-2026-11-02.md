# AWS shutdown — 2 November 2026

Bernard authorized removal of AgriBridge's running AWS infrastructure and
publication of the outstanding project work. DNS and inexpensive recovery/support
resources are retained. The application, Argo CD, Grafana and Prometheus are offline.

## Removed

- All three `k8s.agribridge.deuces.dev` Auto Scaling groups and their EC2 nodes.
  The termination hooks were completed so the nodes could finish terminating.
- The `agribridge-ingress` network load balancer and its target group.
- All nine cluster EBS volumes: three 32 GiB root disks, two 20 GiB etcd disks,
  two 20 GiB PostgreSQL disks, 10 GiB Prometheus and 2 GiB Grafana.
- Five stale runtime DNS records: staging, production, the public/internal
  Kubernetes API and the internal kOps controller. The hosted zone, nameservers
  and ACM validation record are preserved. This avoids pointing names at released
  infrastructure.

## Verification and publication

AWS APIs were used because the local terminal could not resolve AWS or cluster
endpoints. The deletion was scoped by the cluster's ownership tags and VPC.
This was not a successful `terraform destroy` or an orderly Helm uninstall.

The inventory covered all 17 enabled regions for EC2 instances, EBS volumes,
classic/v2 load balancers, NAT gateways, VPC endpoints, EKS, RDS instances and ECS
clusters. No resources in those categories were found outside `us-east-1`.
The final project-region check verifies no active cluster nodes, Auto Scaling
groups, load balancers, target groups, EBS volumes, NAT gateways, allocated Elastic
IPs or VPC endpoints remain. This does not claim the whole AWS account is free.

Publication preserves the latest GitHub branch as its parent, checks changed
files against that revision, and uses an expected-head update without forcing.
Terraform state, generated bootstrap material, `.env`, kubeconfigs, backups and
raw runtime evidence stay outside Git. The curated two-day roadmap is in
`docs/images/agribridge-two-day-roadmap.png`; duplicate generation output is ignored.

Validation: Terraform formatting, shell syntax, Helm lint, 14 GitOps/render
tests, Python parsing, whitespace checks and common credential-pattern checks.
The shutdown commit uses `[skip ci]` to avoid starting an application release
against the offline environments. The deployment workflow remains available for
an intentional future rebuild.

## Before rebuilding

1. Preserve the existing encrypted state and backups. Do not run old saved plans:
   they predate this shutdown.
2. Reinitialize the existing backends. Refresh and review the cluster Terraform
   plan: infrastructure was deleted through AWS APIs, so its state has not been
   reconciled by Terraform. Retained free infrastructure should be reused.
3. Back up the platform state. It still describes Kubernetes/Helm resources in
   the terminated cluster. Review and remove those obsolete state bindings before
   installing the platform into a new cluster; do not blindly apply stale state.
4. Keep the services/bootstrap states and retained secrets. Regenerate the
   kubeconfig and runtime platform inputs after cluster recreation. Recreate the
   runtime DNS records through the corresponding infrastructure/controllers.
5. Restore databases from a suitable logical dump or encrypted snapshot. Keep the
   restored database credentials aligned with the retained runtime secrets.
6. Plan and verify each rebuild stage before enabling GitOps releases again.

Small retained-service charges, earlier usage and delayed billing can still
appear after shutdown. Compute and load-balancer deletion does not erase charges
already accrued.
