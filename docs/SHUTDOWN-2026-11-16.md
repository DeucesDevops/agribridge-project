## Remaining costs and scope

This is a compute and cluster-storage shutdown, not a zero-cost account.
The two retained server disks, snapshot storage, S3 objects, hosted zones,
retained secrets and any applicable requests can still incur charges. Current
credentials and recovery data were kept deliberately. No unrelated stored data
was permanently removed.

Checks covered the account's 17 enabled regions for the main compute/network
services. Additional cache, Aurora, OpenSearch, Lightsail and SageMaker endpoint
checks found no resources where those APIs responded. Lightsail endpoints in
ap-northeast-3 and us-west-1 were unavailable. This inventory is not an exhaustive
billing audit of every AWS product. Cost Explorer returned estimated empty
results and was not used as evidence of a zero balance.

## Bring the project back

1. Keep delivery paused while recovering. Repository settings could not be
   inspected or changed because the browser requires GitHub sign-in. No active
   runs appeared in the latest Actions history. Confirm `DEPLOY_ENABLED=false`
   in repository and environment variables before starting maintenance.
2. Use the current `dev` source and the existing S3 Terraform backends. Preserve
   both Terraform state and the kOps state store.
3. This emergency shutdown used AWS APIs because local network access was
   unavailable. Terraform state still records removed resources. Run a current
   refresh and review new plans; do not reuse saved pre-shutdown plans, delete
   state, or assume the platform is still installed.
4. Start the retained management server if needed, then follow
   [REPRODUCTION.md](REPRODUCTION.md) to recreate the cluster. Review the retained
   etcd recovery section before replacing empty etcd disks.
5. Restore the PostgreSQL volumes from the mapped snapshots, or use verified S3
   database backups. Reconcile the Kubernetes PV/PVC volume identities before
   starting database workloads. Restoring etcd alone does not restore database
   contents. The deleted PV volume IDs must not be reused as if the disks exist.
6. Reconcile platform Terraform state with the recreated cluster, reinstall the
   controllers and monitoring, and let ingress create its replacement load
   balancer. Update DNS to that new endpoint.
7. Verify secrets, storage, backups, rollouts and HTTPS for staging and production.
   Enable delivery only after the platform is ready.
